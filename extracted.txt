PRÉAMBULE — POURQUOI CE DOCUMENT Le cahier des charges EEUEZ Menu V11.0 (Génesis) pose une vision business solide et une ambition réelle. Ce guide ne le remplace pas : il le traduit en décisions d'ingénierie concrètes, opinie par un senior dev, prêtes à être implémentées par l'équipe Antigravity. Trois changements majeurs ont été actés par rapport au CDC original : Le framework Flutter est abandonné au profit de React Native Expo. Un seul codebase JavaScript couvre Android et iOS, le marché caché (Expo Go) permet de distribuer l'app chez les restaurateurs sans passer par les stores pendant la phase MVP, et l'écosystème JS est plus accessible pour recruter localement à Yaoundé et Douala. Le backend passe de toute solution générique vers Spring Boot (Java). Spring Security, Spring Data JPA, Spring Cloud Gateway — tout ce dont on a besoin pour la sécurité bancaire exigée par le CDC est déjà packagé, mature et documenté. La base de données devient hybride : SQLite dans l'app mobile via expo-sqlite (mode offline, survie aux délestages Eneo) et PostgreSQL sur le serveur (multi-tenant, transactions ACID, migrations Flyway). Redis complète le trio pour le cache des menus. 1. STACK GLOBALE ET JUSTIFICATIONS 1.1 Vue d'ensemble Voici la stack retenue dans son intégralité, couche par couche. Le CDC demande une app qui survit aux délestages Eneo — la seule vraie réponse, c'est du stockage local sur le téléphone. SQLite via expo-sqlite stocke en local sur le device : le panier du client, le dernier menu chargé, les commandes en cours du restaurant, la file d'actions à synchroniser. Quand le réseau revient, un job de synchro rejoue tout dans l'ordre. PostgreSQL côté serveur est la source de vérité. Toutes les transactions FCFA, les historiques, les rapports du patron — tout atterrit là en base relationnelle propre avec contraintes et index. Redis entre les deux : les menus changent rarement. Plutôt que taper PostgreSQL à chaque scan QR, on met le menu en cache Redis avec un TTL de 5 minutes. Le menu-service invalide le cache à chaque modification du patron. ! Le SQLite du mobile et le PostgreSQL du serveur ne sont PAS synchronisés directement. L'app envoie des événements métier (créer commande, modifier stock) via API REST quand elle a du réseau. PostgreSQL est la source de vérité. SQLite n'est qu'un tampon local temporaire. 2. STRUCTURE DES PROJETS 2.1 Monorepo recommandé On part sur un monorepo avec deux workspaces indépendants. SCHÉMA BASE DE DONNÉES (PostgreSQL) 3.1 Principes fondamentaux Deux règles d'or qui n'ont pas de négociation possible : Multi-tenant par merchant_id : TOUTES les tables métier ont un champ merchant_id NOT NULL avec un index. C'est la colonne qui isole les données d'un restaurant de celles d'un autre. Sans ça, un bug de routing expose les données d'un restaurant A à un restaurant B. Commission paramétrable : le taux de commission n'est PAS hardcodé à 1% dans le code. Il est stocké en base dans la table merchants (colonne commission_rate DECIMAL(5,4) DEFAULT 0.01). Certains gros partenaires voudront négocier. Anticiper ça maintenant coûte 5 minutes, le changer plus tard coûte une migration en prod. 3.2 Tables principales Table : merchants (les restaurants) CREATE TABLE merchants (   id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),   name              VARCHAR(200) NOT NULL,   owner_phone       VARCHAR(20)  NOT NULL UNIQUE,  -- numéro MoMo principal   city              VARCHAR(100) NOT NULL,          -- Yaoundé, Douala, etc.   quarter           VARCHAR(100),                   -- Bastos, Akwa...   subscription_plan VARCHAR(20)  NOT NULL DEFAULT 'IDEAL', -- LOW_COST|IDEAL|PREMIUM   commission_rate   DECIMAL(5,4) NOT NULL DEFAULT 0.0100,  -- 1% par défaut   is_active         BOOLEAN      NOT NULL DEFAULT true,   momo_merchant_id  VARCHAR(100),  -- ID chez l'agrégateur MoMo   om_merchant_id    VARCHAR(100),  -- ID chez Orange Money   created_at        TIMESTAMP    NOT NULL DEFAULT NOW(),   updated_at        TIMESTAMP    NOT NULL DEFAULT NOW() ); La logique de split (algorithme de répartition) Le CDC décrit un split 1%/90%/10%. L'implémentation correcte en Java : @Service public class CommissionService {     // IMPORTANT : tous les montants sont en FCFA entiers (INTEGER)     // Pas de Double, pas de Float : on ne perd pas de centimes sur les arrondis     public SplitResult calculate(Order order, Merchant merchant) {         int orderTotal    = order.getSubtotalFcfa();         int deliveryFee   = order.getDeliveryFeeFcfa();         // Le taux vient de la base, pas du code         BigDecimal rate   = merchant.getCommissionRate(); // ex: 0.0100         // Arrondi vers le bas : le marchand n'est jamais lésé         int eeuezCommission  = orderTotal.multiply(rate)                                          .setScale(0, RoundingMode.FLOOR).intValue();         int eeuezDelivery    = (int)(deliveryFee * 0.10); // 10% des frais livraison         int livreurCut       = deliveryFee - eeuezDelivery; // 90%         int merchantFinal    = orderTotal - eeuezCommission;         return SplitResult.builder()             .eeuezTotal(eeuezCommission + eeuezDelivery)             .merchantWallet(merchantFinal)             .livreurWallet(livreurCut)             .build();     } } Validation HMAC des webhooks MoMo/OM Un point non documenté dans le CDC mais critique : quand Orange Money ou MTN appellent notre webhook pour confirmer un paiement, n'importe qui peut appeler cette URL en imitant un paiement. La signature HMAC empêche ça. @Component public class WebhookValidator {     @Value("${momo.webhook.secret}")     private String webhookSecret;     public boolean validate(String payload, String signatureHeader) {         try {             Mac mac = Mac.getInstance("HmacSHA256");             mac.init(new SecretKeySpec(webhookSecret.getBytes(), "HmacSHA256"));             String computed = HexFormat.of().formatHex(mac.doFinal(payload.getBytes()));             // Comparaison en temps constant — évite les timing attacks             return MessageDigest.isEqual(computed.getBytes(), signatureHeader.getBytes());         } catch (Exception e) {             return false;         }     } } @RestController @RequestMapping("/api/v1/payment") public class PaymentWebhookController {     @PostMapping("/webhook/momo")     public ResponseEntity<?> handleMomoWebhook(         @RequestBody String payload,         @RequestHeader("X-Momo-Signature") String signature     ) {         if (!validator.validate(payload, signature)) {             // Alerte immédiate au manager             alertService.sendFraudAlert("Webhook signature invalide");             return ResponseEntity.status(401).build();         }         // Traitement normal...     } } Gestion du timeout de paiement (cas non traité dans le CDC) Le CDC ne parle pas du cas où le client ne valide pas son USSD Push. SÉCURITÉ — NIVEAU BANCAIRE 6.1 Architecture JWT Deux tokens, pas un seul. C'est la pratique standard que le CDC ne détaille pas. Token Durée de vie Stockage Usage Access Token 15 minutes Mémoire (pas disk) Toutes les requêtes API Refresh Token 7 jours expo-secure-store (chiffré) Renouveler l'access token L'access token dure 15 minutes pour limiter la fenêtre d'exploitation en cas de vol. Le refresh token est stocké dans expo-secure-store qui utilise le keychain iOS ou le keystore Android — inaccessible depuis une autre app. 6.2 Authentification 2FA pour les managers Les managers et owners ont accès aux rapports financiers et aux retraits. Une simple validation de PIN n'est pas suffisante. Le CDC mentionne le 2FA — voici l'implémentation recommandée : Flux d'authentification manager : 1. Manager entre son numéro de téléphone + PIN sur l'app 2. Le backend valide le PIN (Argon2id hash) 3. Si valide, le backend envoie un OTP à 6 chiffres par SMS (via Orange API) 4. L'OTP expire en 5 minutes 5. Manager entre l'OTP sur l'app 6. Backend valide l'OTP, émet access token + refresh token 7.
